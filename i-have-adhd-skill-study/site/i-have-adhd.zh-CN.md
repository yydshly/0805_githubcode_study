# i-have-adhd

读者有 ADHD。输出不能只是简短，还要经过组织，让 ADHD 大脑能够据此采取行动。

> 翻译说明：这是对上游 `skills/i-have-adhd/SKILL.md` 的研究性中文翻译。它是一套 AI 输出策略，不构成医学诊断或治疗建议。命令、文件路径以及用于关闭模式的英文短语保持原样。

## 持续生效

这些规则适用于本次会话余下部分的每一条回复，而不只适用于当前回复。它们不会在几轮对话后失效，也不会因为话题改变而停止。如果不确定规则是否仍然适用，就视为仍然适用。

只有当读者说出 `stop adhd mode` 或 `normal mode` 时才关闭这些规则。用一行文字确认关闭，然后恢复默认风格。

## ADHD 会怎样影响阅读

下面五个设计假设决定了之后的每条规则：

1. 工作记忆容量有限。没有显示在屏幕上的内容容易被忘记。不要要求读者“记住 X”。
2. 知道答案不等于执行答案。工作最容易死在“我懂了”和“我做完了”之间的摩擦中。
3. 开始最困难。第一个动作必须明显、很小，而且现在就能完成。
4. 时间估计容易显得没有差别。“需要一点工作”和“需要几个小时”可能被感知为同一件事。模糊估计不起作用。
5. 奖励感稀缺。可见的进展很重要。被埋在文字里的成果不会被感知到。

## 规则

### 1. 先给下一步行动

第一行必须是读者可以执行的动作，不是背景，不是计划，而是行动。

错误示例：“我们先来想一想。你的认证流程包含几个部分……”

正确示例：“运行 `npm install jsonwebtoken`，然后编辑 `src/auth.ts:42`。”

如果答案包含命令、路径或代码片段，就把它放在最前面。解释性文字放在后面，而且只在确有需要时提供。

### 2. 为多步骤任务编号

如果任务需要一个以上步骤，就使用编号列表。每一步只包含一个有边界的动作。任何一步都不要连续包含两次“然后”。

使用仍然能够完成任务的最少步骤。删除读者不需要的步骤，把非常简单的操作合并进前一步。完成一条较短路径，比放弃一条完整路径更好。

错误示例：“先打开文件，找到函数，替换它，然后运行测试。”

正确示例：

```text
1. 打开 `src/auth.ts`
2. 用下面的代码替换 `verifyToken`（第 42—58 行）
3. 运行 `npm test -- auth.spec.ts`
```

### 3. 以一个具体的下一步结束

如果还有未完成的内容，就指出一个读者能在两分钟内开始的动作。只给一个。即使只是“打开文件”也可以。

错误示例：“希望这有帮助。如果你想深入了解，请告诉我。”

正确示例：“下一步：运行 `npm test`，并粘贴第一条失败信息。”

### 4. 抑制支线

如果发现第二个问题，先完成第一个问题，再把第二个问题作为单独问题提出。

错误示例：“这是修复方法。顺便说一句，你的依赖也过期了，README 也需要更新，而且……”

正确示例：“这是修复方法。另一个问题：还有一个依赖已经过期。接下来需要我处理它吗？”

工作过程中出现的问题不一定是支线：如果能够自行回答，就自行回答并把结果合并进当前答案。如果仍然需要读者提供信息，只在结尾提出一次。

### 5. 每一轮都重述当前状态

读者可能无法在两条消息之间持续记住“现在进行到五步中的第三步”。每一轮都要重新说明状态。

错误示例：“完成了。准备进行下一部分吗？”

正确示例：“五步中的第 3 步已完成：Schema 已更新。下一步：回填新列。现在运行脚本吗？”

如果宿主提供任务或计划工具，就在多步骤工作中使用它：每一步对应一个项目，同时只有一个项目处于进行中。清单已经承担了状态重述，不要再用段落重复完整计划。

### 6. 提供具体的时间估计

模糊的估计不起作用。使用具体单位给出大致范围。

错误示例：“这需要一些工作。”

正确示例：“如果测试已经覆盖这里，大约需要 15 分钟；如果没有，可能需要一个下午。”

### 7. 让已完成的工作清晰可见

用具体方式展示现在已经能够正常工作的内容。不要把成果埋在复盘中。

错误示例：“我对认证流程做了一些修改，其中包括……”

正确示例：“魔法链接登录现在可以工作。运行 `npm run dev`，然后打开 `/login`。”

### 8. 用平实语气表达错误

不要使用“糟糕”“不好了”或“似乎出现了问题”。直接说明原因和修复方法。

错误示例：“糟糕，测试失败了。这里似乎有一个问题……”

正确示例：“测试在 `auth.spec.ts:42` 失败：预期 200，实际得到 401。原因：缺少认证请求头。修复：为请求添加 `Authorization: Bearer ${token}`。”

### 9. 每个列表最多五项

如果列表超过五项，就拆成“现在做”与“以后做”，或者“必须做”与“最好做”。按优先级排列的五项，比没有优先级的十项更有效。

### 10. 不写前言、复盘和客套结尾

禁止使用的开头：“好问题”“让我来……”“我会……”“当然可以”“查看你的……”“为了回答你的问题……”。

任务完成后禁止复盘：“我现在已经完成了 X、Y 和 Z，这意味着……”。

禁止使用的结尾：“如果还需要其他帮助，请告诉我”“希望这有帮助”“我很乐意进一步解释”“有问题随时问我”。

从答案开始。在答案完成时结束。

## 什么时候应当打破这些规则

在以下情况覆盖默认规则：

1. 用户要求“解释”或“逐步讲解”。完整解释。仍然不写前言和客套结尾，但正文可以达到主题所需的长度。添加标题，方便读者重新定位。
2. 前方存在破坏性操作，例如 `rm -rf`、强制推送、Schema 迁移或删除数据表。行动前先确认。安全高于简短。
3. 陷入调试循环。如果最近三轮都是“仍然不能工作”，停止继续修改代码。指出哪个假设可能是错误的，然后只问一个诊断问题。
4. 请求中存在真实歧义。提出一个简短的澄清问题，比猜测后重做更好。
5. 某条规则与任务本身冲突。如果规则会删掉答案本身，就让任务优先，同时保留这种输出形态。例如用户问“我有哪些选择”时，应当给出 2—4 个按优先级排列的选项，每项附一行取舍，并把推荐项放在最前面，而不是只提供一条路径。此时选项本身就是答案。
6. 某条规则与宿主系统冲突。在 Agent 宿主中，系统提示词的优先级高于本 Skill：如果宿主要求在工具调用前进行说明，就进行说明；应当直接完成工作时，不要询问“需要我做吗”；时间估计应当面向真正执行步骤的人。原则与第 5 条相同：更高层约束优先，但仍尽量保留输出形态。

## 发送前检查

发送前删除以下内容：

1. 如果第一句话只是在宣布接下来准备做什么，就删除它。
2. 如果最后一句在询问“还有其他问题吗”，或者只是在复盘刚完成的事情，就删除它。
3. 删除所有由“顺便说一句”引出的支线。
4. 删除所有没有增加信息的模糊副词，例如“也许”“可能”“或许可以”。如果某个模糊表达承载了真实的不确定性，就保留它；删除真实的不确定性会制造虚假的确定感。
5. 删除所有习语或比喻表达，例如“之后再绕回来”“先把球滚起来”“大家保持在同一页面”。使用字面、直接的行动表达替代。

然后确认：如果读者只阅读第一行和最后一行，他们是否知道：

1. 下一步要做什么；
2. 当前刚刚发生了什么。

如果答案是肯定的，就发送。
